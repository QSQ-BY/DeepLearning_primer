# 9 月 18 日：写完目前最长的 NumPy 项目

这篇日志节选自[项目实验报告](../../简单神经网络运算框架的实现/docs/lab_report.md)，记录的是我在实现过程中感受最深的部分，想要对项目有更完整的了解可以直接看我的实验报告。

## 4. 真正困难的是把公式写成代码

如果只看最后的公式和作用，很多层似乎并不复杂。真正开始写以后，我才发现“看懂公式”和“能写成可靠的 NumPy 代码”完全不是一回事。公式可以省略很多默认关系，代码却必须明确每个轴、每次广播、每个缓存和每一个需要累加的位置。

卷积反向传播是整个项目里最难的一段。前向传播中的一个输入位置可能被多个滑动窗口覆盖，同一个卷积核也会用于所有样本和空间位置。因此，输入梯度和权重梯度不能简单赋值，而要把每一次贡献累加起来：

```python
gradient = grad_output[
    batch_index,
    output_channel,
    output_row,
    output_column,
]
self.grad_weight[output_channel] += input_window * gradient
grad_padded_input[
    batch_index,
    :,
    row_start:row_end,
    column_start:column_end,
] += self.weight[output_channel] * gradient
```

这里最重要的是两个 `+=`。纸面上写一句“根据链式法则求和”很快，代码却必须找到正确的窗口，把不同输出位置的梯度放回同一片输入区域。再加上批次、输入通道、输出通道、步幅和填充，四维数组很容易在脑中混在一起。

BatchNorm 又是一个很大的难点。它的公式更集中，这里我偷了一点小懒，直接找的现成的公式，并没有像线性层和卷积层那样去想它具体的复杂推导，但后续的实现还是很不容易，训练和推理走的是两套统计量，二维输入与四维输入的归约轴也不同。我必须同时处理广播形状、运行均值、运行方差和反向传播缓存。以前看到“按通道归一化”时觉得意思很清楚，实际写代码才知道这句话至少还缺少统计轴、参数形状和模式状态。

这次实验最直接地改变了我对“理解”的判断。现在如果我只会复述公式，却说不清数组是什么形状、梯度要沿哪些轴求和，我不会再觉得自己已经真正掌握了这一层。

## 5. 测试也是实现过程的一部分

这个项目的开发过程大体按 TDD 的思路推进：先确定一个很小的行为，写出测试并看到它失败，再补上能让它通过的实现，最后运行完整回归。

我以前更容易把测试理解成代码写完后的检查。这次测试直接参与了实现。比如卷积层不是一次写完，而是先检查类和参数形状，再处理单通道前向、多通道、stride、padding，最后拆开检查偏置、权重和输入梯度。面对一个很长的反向传播函数时，这种顺序让我至少知道当前只需要想清楚哪一件事。

测试还逼着我处理正常例子之外的情况：没有调用 `forward()` 就执行 `backward()`、上游梯度形状错误、IDX 魔数不正确、文件数据被截断、图片和标签数量对不上等等。

现在回头看，项目里大部分 Python 代码行数其实在 `tests/`。测试不是给读者从头读到尾的，我却在上面花了很多时间。每写一个用例，我都得想清楚网络该怎么用、输入必须满足什么条件；这既是在练代码，也是在学自己写出的每一层到底做了什么。

写测试还让我学会用 `unittest.TestCase` 组织用例，用 `with self.subTest(...)` 检查不同配置，配合 `with tempfile.TemporaryDirectory()` 和 `try/except/else` 测试文件读取与异常。检查错误形状时，我现在会问得更具体：它该报哪种错，提示能不能让我找到传错的维度？

## 6. 这不是我独立从零写出的项目

说实话，这个项目不能算是我一个人从空白独立写出来的。整个过程都是跟着 Codex 老师一步步推进的：先解释公式和形状，再把任务拆小，给出代码骨架，我继续填写、运行并修改。项目中相当一部分代码是我跟着示例“抄”下来的，真正完全由我自己设计并写出的部分很少。

这一点需要写清楚。我可以说自己把这些代码敲进了项目，也跟着测试走完了实现过程，但还不能说离开提示以后，我已经能完整重写所有层的反向传播。尤其是 Conv2D 和 BatchNorm，很多细节仍然需要回头看公式与现有实现。

不过，亲手把代码输入、运行、看见错误，再沿着错误查回去，和只看一份现成代码并复制粘贴还是有区别。至少我现在知道困难具体在哪里，而不是仅仅让流程在自己的脑子里简单过一遍。
