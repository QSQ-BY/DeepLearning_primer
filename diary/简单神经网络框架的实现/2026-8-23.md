## 8 月 23 日：开始搭自己的神经网络运算框架

完成 Softmax 后，我开始做一个只依赖 NumPy 的简单神经网络运算框架。这个任务最终要实现全连接层、卷积层和 Batch Normalization 的前向传播与反向传播，但目前还处在第一阶段：先把包目录、测试目录、示例目录和设计文档搭起来，再从最小的 `Linear` 层开始。

我跟着 Codex 老师从零建立了这一套开发流程。现在的 `Linear` 已经能够创建权重和偏置，并完成 `y = x @ weight + bias` 的前向传播。权重使用适合 ReLU 网络的 He 初始化，偏置从 0 开始；需要复现实验时，还可以从外部传入带固定种子的 NumPy 随机数生成器。

真正让我吃惊的是当前的开发过程一直在追问“错误输入进来时应该发生什么”。例如，前向传播不只要算出正确结果，还要先检查输入是不是二维数组、特征数能不能和权重对应：

```python
def forward(self,x):
    if(x.ndim != 2):
        raise ValueError(
            "Linear input must be a 2D array"
        )

    expected_features = self.weight.shape[0]
    received_features = x.shape[1]
    if(received_features != expected_features):
        raise ValueError(
            f"Linear expected {expected_features} input features, "
            f"but received {received_features}"
        )
    return x @ self.weight + self.bias
```

测试里还会故意传入形状错误的数据，确认代码抛出的不仅是某个异常，而且必须是合适的 `ValueError`，错误信息也要让调用者看得懂：

```python
try:
    layer.forward(wrong_x)
except ValueError as error:
    self.assertIn(
        "expected 2 input features",
        str(error),
    )
else:
    self.fail(
        "Linear.forward() should reject the wrong feature count"
    )
```

这段测试让我真正理解了 `try`、`except` 和 `else` 在测试中的配合。抛出预期的 `ValueError` 后，`assertIn()` 继续检查错误信息；如果什么异常都没有，`self.fail()` 就主动让测试失败；如果抛出的是其他异常，测试会直接显示错误。这比“只要程序报错就算检查成功”严格得多，因为不同异常往往代表完全不同的问题。

一开始我以为实现神经网络框架，应该直接从矩阵公式和反向传播写起。没想到当前这一步很大一部分是由错误输入和失败测试带着向前走：先决定接口应该怎样使用、哪些输入必须拒绝，再补上刚好能够满足约定的实现。它和 Softmax 的公式没有直接关系，却让我第一次比较具体地接触到真实项目里的接口设计、异常处理和测试方法。

现在回头看，这些检查并不是在给代码加一些无关紧要的限制。一个小练习里，矩阵维度错了也许看一眼报错就能改；等到多个层连接起来以后，如果错误一直传到更深的矩阵运算才爆出来，定位会困难得多。让 `Linear` 在自己的边界上给出明确的错误，实际上是在替后面的使用者保留线索。

这三天的收获因此分成了两条线：一条是完成 Softmax 分类；另一条是我开始知道，一个能长期扩展的项目不能只有“正常输入时能跑”的代码。下一步要实现 `Linear.backward()`，那时既要推导输入、权重和偏置的梯度，也要继续为这些行为写测试。等反向传播真正跑通，深度学习里的数学和这几天学到的工程流程才会第一次接在一起。
